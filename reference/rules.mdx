Rules are the principles the Council enforces. Every Council-mediated task applies the rules that match its file types and scope. There are two tiers: **Floor rules** — 26 concise files in `rules/common/` that are always loaded and active on every task — and **Library rules** — 187 on-demand files in `rules-library/` that are lazy-loaded when skill or agent invocations, file-type matches, or adaptive workflow conditions call for them. Floor rules encode the absolute baseline; Library rules carry the detailed standards references, language-specific guidance, and operational playbooks that would bloat the context budget if preloaded unconditionally. Per the global-vs-project classification rule, all rules in this catalog are pure guidance; project-specific facts live in `<workspace>/.claude/rules/`.

**Rule counts**

- **`rules/common/`** — 26 concise Floor rules. With `CLAUDE.md`, 19,428 bytes on 2026-09-28 (bytes/4 estimate: 4,857 tokens; not billed usage). Measure with `node scripts/token-budget.mjs --root . --check`.
- **`rules-library/council-detail/`** — 27 preserved detailed references; read only relevant sections under the current adaptive workflow.
- **`rules-library/common/`** — 60 lazy-loaded universal rules.

## Library rules and the lazy-loading model

Library rules live under `rules-library/` and are never preloaded unconditionally. Instead they are loaded on demand — triggered by skill or agent invocation, by a file-type match in the `auto-skills.md` mapping, or by an explicit adaptive-workflow condition. This keeps the eager context budget under its 24,576-byte CI cap while still making the full 187-rule library available whenever the task warrants it.

The lazy-loading contract has three parts:

1. **Always-on global rules** load on every file touch. The `auto-skills.md` rule lists the "global rules that auto-load on EVERY repo touch" section explicitly.
2. **File-type-mapped rules** load per the file-to-rule mapping in `auto-skills.md`. Touching a `*.go` file loads the `golang/*` rule set; touching a `*.tsx` file loads the `typescript/*` rule set; and so on.
3. **Workspace rules** in `<workspace>/.claude/rules/` layer on top additively. Workspace rules may **raise** thresholds (stricter) but never **lower** them (looser). When layers conflict, the strictest wins.

Per-line suppressions (`// eslint-disable`, `// @ts-ignore`, `# noqa`, `//nolint`, etc.) are **banned everywhere**. If a rule is wrong for the context, the project configuration changes — never the per-line directive.

## How to author a rule

Adding a rule to the global Council follows a five-step process drawn from the contributing guide.

**Step 1 — Follow the principal-level template.** Every rule carries: a one-line summary, a core-principle paragraph, numbered hard-rules with WRONG/CORRECT side-by-side examples, a verification block, cross-references, a "Why this rule exists" section explaining the failure mode and cost, and learning hooks tied to the continuous-learning mandate.

**Step 2 — Pick the location.**

- Universal guidance → `rules/common/<name>.md`
- Language-specific extension → `rules-library/<lang>/<name>.md`
- Project-specific → `<workspace>/.claude/rules/<name>.md`

**Step 3 — Cite primary sources.** Every rule that depends on external standards must cite the authoritative reference with version and section (for example, `WCAG 2.2 §1.4.3`, `OWASP ASVS 4.0.3 §2.1.7`, `RFC 9110 §9.3.1`). Stack Overflow, npm READMEs, and blog posts are not acceptable sole references.

**Step 4 — Add anti-patterns, cross-references, and a verification checklist.** The anti-patterns table names what to reject, why, and the correct alternative. Cross-references link to sister rules, skills, and agents. The verification checklist carries concrete green/red predicates, not aspirational language.

**Step 5 — Run `tests/verify-standards-citations.sh` locally.** This is the same gate CI runs. All four verifiers (`bootstrap/verify.sh`, `tests/verify-link-integrity.sh`, `tests/verify-no-orphans.sh`, `tests/verify-standards-citations.sh`) must pass before opening a PR.

## Global vs. project rule decision guide

Before writing any new rule, determine whether it belongs in the global Council or in a project-specific `.claude/rules/` directory. Per `rule-authoring-global-vs-project.md` and the contributing guide:

| Question | Answer → goes in |
| -------- | ---------------- |
| Is this guidance applicable to every codebase you work on? | Global (`rules/common/`, `skills/`, `agents/`) |
| Is this guidance tied to a specific project's stack, vendor, architecture, or domain model? | Project (`<workspace>/.claude/rules/` etc.) |
| Could it be split into a generic principle + a project-specific config? | Both — global principle + project config (canonical shape) |

When in doubt: write the principle in global, the specifics in project. Global rules must justify their recurring context cost. Put detailed examples in on-demand references and give the short entrypoint a clear activation condition. No project or workspace names, no vendor brand names from a specific project's vendor list, no per-project file paths, and no session-specific dates are permitted in global rules.
