Skills are reusable patterns and methodologies — the positive counterpart to rules. Where a rule says "do not write X," a skill says "here is how to design Y." Each skill encodes principal-level guidance for a specific problem class: concrete patterns, named trade-offs, authoritative standards citations, anti-pattern tables, and a verification checklist. Skills are selected by description, task relevance, or explicit invocation. File `paths:` metadata acts as a rule-scoping suggestion for auto-routing, not as automatic skill activation — a skill can fire on any task where its guidance is relevant, regardless of file type. The context policy keeps detailed guidance on demand: skill entrypoints are concise, and detailed reference sections load only when the task warrants them.

## Skill structure

Per the principal-level mandate, every skill uses the following elements where they help the task. Short skills need not repeat a large fixed template:

- **Purpose** — why this skill exists; what problem class it solves
- **Standards Cited** — primary-source references with version + section (RFC / ISO / NIST / OWASP / W3C / WCAG / IFRS / ITIL)
- **When to Fire** — file globs / keywords / scope conditions
- **Core Patterns** — concrete examples with named trade-offs
- **Anti-Patterns** — what to reject + why + named alternative
- **Verification Checklist** — concrete green/red predicates
- **Cross-References** — sister rules, skills, agents
- **Why This Skill Exists** — failure mode it prevents + cost of getting it wrong

## How to invoke a skill

Skills can be activated in three ways:

**1. By name in a prompt.** Explicitly name a skill to load it regardless of the current file context:

```text
Use the payment-processing-patterns skill to review this checkout flow.
```

**2. By task relevance (automatic).** The Council selects skills based on description and task relevance. When a task matches a skill's "When to Fire" conditions — keywords, scope, problem class — the skill fires silently without a slash command or explicit invocation.

**3. Via `paths:` metadata routing.** Some skills declare `paths:` frontmatter that maps file globs to skill invocation. This is a rule-scoping mechanism for file-type routing, not a guarantee of activation — the skill can still fire on any task where its guidance applies.

A few examples of auto-fire patterns from `auto-skills.md`:

- Touching a `*.go` file auto-fires: `golang-patterns`, `golang-testing`, `coding-quality-rules`, `security-review`, `tdd-workflow` — and engages agents: `go-reviewer`, `go-build-resolver`, `tdd-guide`, `security-reviewer`.
- Touching a `*.vue` UI file auto-fires: `frontend-patterns`, `vue3-patterns`, `coding-quality-rules` — and engages: `code-reviewer`.
- Touching a payments-related file (`payments/`, `billing/`, `checkout/`, `stripe/`, `escrow/`, `wallet/`, etc.) auto-fires: `payment-processing-patterns`, `pci-dss-patterns`, `bookkeeping-patterns`, `security-review`, `owasp-asvs`, `soc2-readiness` — and engages: `payments-reviewer`, `compliance-reviewer` (VETO), `security-reviewer`, `finance-reviewer`, `risk-reviewer`.

## Skill structure in detail

Every skill under `skills/<name>/SKILL.md` is authored against the principal-level template. The elements, and what each must contain:

| Element | What it must deliver |
| ------- | -------------------- |
| **Purpose** | Why this skill exists; what problem class it solves; what it does NOT solve (negative scope is as important as positive scope) |
| **Standards Cited** | Authoritative references with version + section — WCAG 2.2 §1.4.11, OWASP ASVS 4.0.3 §2.2.1, ISO/IEC 27001:2022 Annex A.8.7, RFC 9110 §9.3.1 |
| **When to Fire** | Triggers: file globs, keywords, scope conditions, plan-tier impact |
| **Core Patterns** | Principal-level patterns with concrete examples, named trade-offs, inflection points |
| **Anti-Patterns** | What to reject + why + the named alternative (≥5 anti-patterns with named alternatives required) |
| **Verification Checklist** | Concrete checks — not aspirational; each check has a green/red predicate |
| **Cross-References** | Sister rules, sister skills, agents that pair with this skill (≥3 required) |
| **Why This Skill Exists** | The failure mode this skill prevents; the cost of getting it wrong vs the cost of the rigor |

The quality floor for any skill contributed to the global Council: ≥ 500 words of substantive content (target 1,500–3,000 for complex domains), ≥ 3 authoritative standards citations with version and section, ≥ 5 anti-patterns with named alternatives, ≥ 1 verification checklist with concrete checks, ≥ 3 cross-references to sister rules/skills/agents, and zero project-specific names, paths, or vendor identifiers.

## How to add a skill

Adding a skill to the global Council follows the same principal-level bar as adding a rule. The full process — including how to pick the right cluster, how to author the skill template, how to add the file-type mapping in `auto-skills.md`, and how to run the verifier suite before opening a PR — is documented in the [contributing guide](https://github.com/Nmor/the-claude-council/blob/main/docs/CONTRIBUTING.md).

<Note>
Skills are never project-specific names, workspace paths, or vendor identifiers. Zero "shallow stub" language ("see X for details" without details) is permitted. If none of the 13 existing clusters fits your skill, propose a new cluster in the PR description.
</Note>
